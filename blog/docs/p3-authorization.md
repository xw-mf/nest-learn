# P3 · 授权体系：越权思维——服务端是最后的防线

> 项目：blog（Nest v12 + Prisma 7）
> 本章目标：落地 RBAC（角色）+ 资源归属校验（所有权）双层授权，建立"越权思维"。
> ⚠️ 全场景实测通过（横向越权 403、纵向越权 403、管理员放行、软删除生效）。
> 💡 前端类比：前端隐藏按钮 ≈ "劝你别点"；后端授权 ≈ "点了也没用"。**前端的权限控制是用户体验，后端的权限控制才是安全**。

---

## 本章的后端思维主题：越权思维

前端做权限的思路是"控制界面"：没权限就隐藏按钮、隐藏菜单。这对用户体验完全正确，但**对安全毫无作用**——攻击者不经过你的界面，直接 curl 调 API。

后端授权要防两类越权（面试必考）：

| 类型 | 别名 | 场景 | 本章防线 |
|---|---|---|---|
| **纵向越权** | 提权 | 普通用户调用管理员接口（`GET /users`） | `RolesGuard`（角色检查） |
| **横向越权** | IDOR（不安全直接对象引用） | 改 URL 里的 id，操作**别人**的文章 | `OwnershipGuard`（归属校验） |

关键认知：**角色（Role）解决"你是什么级别"，归属（Ownership）解决"这是不是你家的东西"**——两个维度缺一不可。只有 RBAC 没有归属校验的系统，任何登录用户都能改任何人的数据。

## 知识点释义

### 1. 授权的执行位置：必须在服务端

```text
前端：隐藏"删除"按钮      → 用户体验（防误触）
后端：OwnershipGuard 403   → 安全（防攻击）
```

为什么必须在服务端？回到 P2 的信任边界：**请求可以来自任何地方**，攻击者直接构造 HTTP 请求，前端的一切约束都不存在。服务端是"唯一能强制执行规则的位置"——这就是"服务端是最后的防线"。

### 2. 第一层：RBAC 角色守卫（纵向）

角色检查的全局守卫（`RolesGuard`），配合元数据声明：

```typescript
@Get()
@Roles(['ADMIN'])  // 声明式：这个接口只有管理员
findAll() { ... }
```

守卫链顺序（实测 ✅）：**全局 `AuthGuard`（认证：你是谁）→ 全局 `RolesGuard`（授权：你什么级别）→ 方法级 `OwnershipGuard`（归属：是不是你的）**。

- 401 = 认不出你是谁（没登录）
- 403 = 知道你是谁，但你没资格（角色不够/不是所有者）

### 3. 第二层：资源归属守卫（横向，实测 ✅）

```typescript
@Injectable()
export class OwnershipGuard implements CanActivate {
  async canActivate(context: ExecutionContext) {
    const req = context.switchToHttp().getRequest();
    const article = await this.prisma.article.findUnique({ where: { id } });
    if (!article || article.deletedAt) throw new NotFoundException('文章不存在');

    const user = req.user;
    if (user.role === 'ADMIN') return true;           // 纵向放行
    if (article.authorId !== user.sub) {
      throw new ForbiddenException('只能操作自己的文章'); // 横向拦截
    }
    req.article = article; // 顺手挂上去，控制器省一次查询
    return true;
  }
}
```

实测：

```text
S3 用户B 改用户A 的文章 → 403 "只能操作自己的文章"   ← 横向越权被拦
S4 作者本人改           → 200
S5 管理员删别人的文章    → 200（纵向权限）
```

**设计细节**：守卫里查出文章后挂到 `req.article`——10 章的分工原则："有 DI 的机制（守卫）干活，控制器/装饰器取值"。

### 4. 404 vs 403：存在性也是情报（安全细节）

注意守卫里的顺序：**先查存在性（404），再查归属（403）**。

如果顺序反过来（先报 403"不是你的"），等于告诉攻击者"**这个 id 的文章存在，但不是你的**"——泄露了资源存在性。标准做法：资源不存在**或**不是你的，对外都表现一样（很多系统甚至统一返回 404）。我们的实现里"不是你的"返回 403 是开发友好型选择；更严苛的系统选 404。

### 5. 软删除落地（P1 设计的兑现）

`remove()` 不物理删行，而是写 `deletedAt`；所有查询统一过滤 `deletedAt: null`。实测：删除后公开列表少一篇、详情 404，但**数据库里数据还在**（DBeaver 可查）——误删可恢复、审计有依据。

### 6. 踩坑实录（梅开二度）：`import type` 又坑了我一次

P2 文档里我刚写完"DTO 禁用 `import type`"，本章 `articles.controller.ts` 里我又写了一次——症状一模一样（字段全丢、校验失效）。**这就是为什么团队需要 lint 规则/CR 清单：知道和做到之间隔着一次 500**。已修复并再次验证。

## 动手练习

1. **评论的授权**：给博客加评论接口（`POST /articles/:id/comments` 登录可发；`DELETE /comments/:id` 只能删自己的评论，ADMIN 可删任何评论）。复用 `OwnershipGuard` 的模式，但注意资源从 Article 变成了 Comment——想想守卫怎么写得通用一点（提示：参数化资源类型）。
2. **404/403 统一实验**：把 `OwnershipGuard` 里"不是你的"也改成抛 `NotFoundException`，对比两种响应对攻击者的信息差。
3. **草稿的可见性**：现在公开列表只显示 `published: true` 的文章。作者本人应该能看到自己的草稿。实现 `GET /articles/mine`（登录后看自己的全部文章，含草稿）。
4. **概念题**：`RolesGuard` 和 `OwnershipGuard` 为什么拆成两个守卫而不是合成一个？（提示：职责单一 + 执行位置不同——全局 vs 方法级）
5. **概念题**：如果前端做了完整的路由守卫和按钮隐藏，后端可以省掉授权校验吗？为什么？

---

## 练习参考答案

**练习 4**：两个原因。① **职责不同**：RolesGuard 回答"什么级别能进这个接口"（路由级，和具体资源无关，可以全局跑）；OwnershipGuard 必须查数据库拿到具体资源才能判断（资源级，只适合挂在需要它的方法上）。② **执行成本不同**：归属校验要查库，全局跑会给每个请求都加一次无谓的数据库查询。拆分让"便宜的检查全局跑、昂贵的检查按需跑"。这也是授权设计的通用原则：**先粗后细，先便宜后昂贵**。

**练习 5**：不能，理由就是本章思维主题——**请求可以绕过前端直接到达服务端**。前端隐藏只是"不引导"，不构成"不可能"。真实事故里的越权几乎全是"前端确实藏了按钮，但后端没校验"。记忆口诀：**UI 权限是体验，API 权限才是安全**。

（练习 1 验证标准：路人乙删甲的评论 403，本人/ADMIN 可删；练习 3 验证标准：`/articles/mine` 返回草稿而公开列表不含草稿。）
